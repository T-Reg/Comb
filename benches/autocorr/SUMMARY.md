# Step 2A.6 change autocorrelation — results by file type (2026-10-29, hive)

- `by-type/SUMMARY-by-type.md` — every series × type × window in one table (generated by `scripts/gather.py`)
- `scripts/` — everything that produced these (`run-all2.sh` is the entry point)
- Raw data is not in git. Per-anchor tables (`by-type/<series>-<type>-h<window>.md`), composition
  breakdowns (`<series>-breakdown.md`), the superseded 3-largest-files `first-run/` and `logs/` are
  archived on hive in `~/comb-archive/autocorr-2026-10-29/` (`local-benches-autocorr.tar.xz`, plus
  `hive-results-and-logs.tar.xz` with the raw `results*/` and run logs; checksums in `SHA256SUMS`).

**Method.** Per release, every file of a type is concatenated in path order (version numbers
stripped from paths so they line up across releases) and `autocorr` runs on the concatenations;
"all" is the whole release. SteamOS is split by GPT partition instead.

## How to read the ratios

(B) says that **the parts that just changed are the parts most likely to change next.** Take three
consecutive releases A → B → C and split B's chunks into **new** (absent from A, so just changed) and
**old**. Then ask what fraction of each group is gone in C.

*Example: SteamOS rootfs, snapshot .2 → .3 → 3.1, 2 KiB chunks.* Picture B as 1,000 chunks:

| | chunks | gone in C | rate |
|---|---|---|---|
| all of B | 1,000 | 85 | **base** = 8.5% |
| new in B (`new %` = 5.7) | 57 | 56 | **conditional** = 98% |

**ratio = conditional ÷ base = 0.98 ÷ 0.085 ≈ 11.5**: a chunk that just changed is 11.5× more
likely to change again than an average chunk. Random change would give ≈ 1; well above 1 supports
(B); below 1 means "changed once, then settled" (e.g. a map edited once).

**max.** Conditional cannot exceed 100%, so the ratio can never exceed **max = 1 ÷ base**:

| base (share changing per release) | 5% | 10% | 50% | 90% (compiled code) |
|---|---|---|---|---|
| highest possible ratio | 20 | 10 | 2 | 1.1 |

So when nearly everything changes every release, the ratio is stuck near 1 whatever the truth.

**How to read a row:**

| what you see | example | meaning |
|---|---|---|
| ratio far above 1, max high | Wesnoth 11.0, max 13.3 | **evidence for (B)**: room for any answer; the data chose clustering |
| ratio ≈ max ≈ 1 | Blender `.exe` 1.09, max 1.11 | **no information**: everything changes, the test cannot tell |
| ratio near 1, max high | none in these results | **evidence against (B)**: room for clustering, but change was random |

A ratio right at its max (SteamOS rootfs: 11.5 vs 11.8) is the strongest case: nearly every chunk
that changed, changed again. Ignore huge ratios when `new %` is tiny (≈ 0.1%: a few chunks).
Numbers below are the **median over release triples at h = 2 KiB**; the pooled figure is dragged
toward the ceiling of the highest-churn triple, so read the median first.

## Verdict

**(B) is supported wherever the data can test it.** Every series and type with headroom shows
change clustering, mostly strongly: Wesnoth 11.0, Mindustry 9.4, SteamOS 8.2 (rootfs 6.6,
both triples at their ceiling), 0 A.D. 2.8 (whole release). Nothing with headroom came out near 1. What does not support (B) is not
evidence against it either: compiled code changes ~80–95% every release, so its ratio is pinned
at a ceiling of ~1.1–1.3.

The threshold is still not pinned in PLAN.md. With medians of 9–14 on the asset-heavy series it
would take a threshold above ~3 to change the outcome for those; 0 A.D. (2.8) is the one series
where the choice matters.

## What this means for Comb

1. **Assets split into two populations**, which is exactly the shape (B) exploits: bulk media
   (audio, most textures) barely changes from release to release, and the parts that do change
   (atlases, translations, scripts, config, OS packages) keep changing in the same places.
2. **Compiled code is a write-off for any chunking scheme**: ~80–95% new every release.
   Releases that are mostly code (OpenMW, Blender, Luanti) will see little benefit from Comb at
   any tier. For content-heavy games it is 7–31% of bytes.
3. **Archives are not automatically a problem.** 0 A.D.'s zip compresses entries individually,
   and the results with and without unpacking are nearly identical. Solid archives (.zst, .gz,
   whole-file compression) stay opaque.
4. **Generated files can be pathological**: CDDA's `.mo`/`.json` and Blender's `.mo` are
   ~85% new every build, while Wesnoth's `.mo` is 9% new. It depends on how the build tooling
   orders output, not on the file type.

## Caveats

- **SteamOS:** release order verified from `os-release`: recovery-1 (20220227.2) → recovery-2
  (20220227.3) → recovery-3 (20220425.2, 3.1) → recovery-4 (**the same build** as recovery-3,
  re-issued) → repair (20231117.11, 3.5.6). The table uses the deduplicated run
  (`by-type/steamos_dedup-*`, recovery-4 dropped); `by-type/steamos-*` includes it. Its last
  step spans 18 months (3.1 → 3.5.6, base 0.6), so that triple's ratio is capped at 1.7 even
  though 99.6% of the chunks new in 3.1 were gone by 3.5.6. Only 2 triples: more SteamOS
  releases between 3.1 and today would firm this up.
- **CDDA:** consecutive nightly builds alternate between ~100% and ~2% new. They may come from two
  branches or build configs; `VERSION.txt` does not say. Its numbers are not trustworthy until
  the series is split.
- **0 A.D.:** only 0.0.11–0.0.22 (2012–2017); see below for 0.0.23+.
- Medians come from 3–13 triples per series; triples overlap, so they are not independent.

## Getting 0 A.D. 0.0.23+ working

The installers are NSIS, but from 0.0.23 on the payload is in a form that Ubuntu's 7-Zip 23.01
and Debian's 7-Zip 25.01 both refuse ("Cannot open the file as [Nsis] archive"); 0.0.11–0.0.22
open fine. Options, best first:

1. **Use the Linux data tarballs instead**: `0ad-<ver>-alpha-unix-data.tar.xz` from
   releases.wildfiregames.com is the same game data (the 84%+ that matters) as plain `tar.xz`;
   extracting needs only `tar`. Add them to the fetcher and the corpus manifest.
2. **Run the installer silently**: on the Windows desktop `0ad-<ver>-win64.exe /S /D=D:\CombCorpus\0ad\raw\<ver>`
   (NSIS silent install), or under Wine in a container on hive.
3. **Try 7-Zip's own Linux build** (`7zz` from 7-zip.org). Untested: the sandbox blocked
   downloading and running it from here. Run it yourself if you want to check.
